## Plan Review: Warm-Dispatch Latency Measurement Implementation Plan

**Verdict:** REVISE

The rewrite since review 1 closed almost every structural objection that review raised: the Open Decisions are gone, the infeasible key-mutation route is gone, the cost model for `B` is corrected and verified, the harness is committed rather than hand-rolled a fourth time, cleanup is asserted positively because the artefacts are gitignored, and the post-hoc threshold relaxation is recorded as a deviation instead of being dressed as pre-registration. Eight lenses independently praised the instrument design — interleaved pairs, a seeded paired bootstrap, a pre-registered taxonomy with an explicit no-optional-stopping rule, and a per-sample gate aimed squarely at the `--fail-safe` swallow that would manufacture a pass out of fast failures.

What survives is concentrated in four places. The plan's **references into the documents it must edit have drifted**: 0189 has twelve acceptance criteria with the latency criterion at **number 10**, so Phase 1's instruction to tick "1 to 10" ticks the very criterion Phase 4 is meant to decide, and all five stale-passage anchors plus both `sha256_file` call-site anchors resolve elsewhere. **Phase 3 contradicts itself on where the baseline lives** — a `chmod +x` into the launcher's live cache root under the `store::TEMP_PREFIX` reserved namespace, three paragraphs above the argument that this is exactly what must not happen — and the abort checklist verifies the forbidden path. **The envelope normaliser's specification cannot be implemented**: the Rust function it claims to port returns `("allow","")` for empty stdout, which is the same conflation the plan condemns elsewhere, and has no legacy-shell branch at all, so a faithful port aborts on the first `B` sample. And **the one argument that selects 1.4 over the 1.3 floor of the author's own band is refuted by the plan's own sizing rule** — half-width is purchasable at the n the plan already budgets for escalation, which makes 1.3 decidable too.

Four criticals and twenty-six majors after deduplication, across eight lenses.

### Cross-Cutting Themes

- **Citation and numbering drift is systemic, not incidental** (flagged by: Documentation, Correctness, Standards) — the criterion ordinals are off by one with a phantom criterion 13; all five 0189 stale-passage anchors are stale by 15–49 lines, one of them now pointing at the acceptance criteria a different step edits; the two `sha256_file` call sites are at `:291`/`:295`, not `:288`/`:291`, which the plan's own cited source (0205) records correctly. This matters because Phase 1 and Phase 4 transcribe these numbers verbatim into three work items and two closed 0169 documents, where they become the permanent record.
- **The baseline's location is specified twice, incompatibly** (Correctness, Safety, Standards, Architecture) — the recovery command writes `bin/.tmp-vcs-guard-baseline`; the same section then argues the baseline must live in a temp dir `T` because `bin/` is the live cache root and `.tmp-` is `store::TEMP_PREFIX`. Both hazards are verified real. The abort checklist and two success criteria assert the forbidden path, so if `T` is used they pass vacuously while an unreviewed executable and a symlink into the live `scripts/` go uncovered.
- **The normaliser is specified against an oracle that contradicts the requirement** (Test Coverage, Architecture, Correctness, Standards) — "must match `guard_decision_table.rs:99-141`" and "empty stdout must be distinguishable from allow" are jointly unsatisfiable; the Rust function additionally lacks the legacy shell branch and labels anything carrying `permissionDecisionReason` as `block` without checking `permissionDecision == "deny"`. Correctness further notes the *rationale* is inverted: under an expected-`block` comparison, a deny→allow mapping produces a loud abort on sample one, not a silent pass.
- **The gate's statistic is chosen at each point in the direction that favours the expected verdict** (Performance, Correctness) — the 1.4-over-1.3 justification collapses under the plan's own sizing rule; raw medians are labelled "the conservative direction for a gate" when the plan's own algebra shows they are the *lenient* one; the bash-floor-subtracted ratio is 1.358, leaving ~3.5 half-widths of margin rather than the claimed ten. Each choice is individually defensible; the pattern is what the reframing's own deviation record exists to guard against.
- **Everything that protects the measurement's validity sits in the untested half** (Test Coverage, Architecture) — the TDD'd core holds statistics; the excluded "thin driver" holds the precondition scan, the per-sample gate, the inode/mtime witness, the CPU-count rung chain, the backend `PATH` switch and cleanup. A defect there yields a plausible number rather than a crash, in a session that runs once. The repo already tests this class of code with injected doubles (`tests/unit/tasks/shared/doubles.py`, `test_limits.py`'s monkeypatched `resource`).
- **The recovery mechanism detects but does not remediate** (Safety, Correctness) — every abort-checklist item bar 5 is a post-condition assertion, so on the trap firing mid-run item 1 fails immediately and nothing is specified to remove the baseline or fixture; item 6 puts a multi-minute `mise run cli:check` inside a `trap … INT TERM` handler, scoped to a workspace no phase mutates.
- **The criterion is narrowed to a host configuration that no CI lane and no stock macOS install provides** (Portability, Performance, Correctness) — the gate binds hosts resolving `sha256sum`, which `macos-latest` does not; the configuration most users have is predicted at ratio ~1.79 and is left with no criterion, no threshold and no owner, routed to a 0191 the plan simultaneously declares no longer a co-requisite.
- **The corpus sweep is incomplete on its own terms** (Documentation) — after Phase 1, 0189 still asserts `G ≤ 1.1 × B` in three unenumerated passages including an Assumptions bullet this plan directly falsifies; 0205 closes `done` with eight unticked criteria and a stale "Blocks:" edge, reproducing verbatim the orphaned-record failure the plan's own Current State Analysis condemns.

### Tradeoff Analysis

- **Fixture depth: pinned constant vs irrelevant**: Portability argues fixture depth must be pinned because macOS `$TMPDIR` is seven or eight components deep against linux `/tmp`'s one, inflating `B` by several `dirname` spawns and biasing the darwin gate toward passing. Correctness argues the term is zero at any depth, because `find_repo_root` tests `-e "$dir/.jj"` on `$PWD` before its first `dirname` call and the subprocess cwd *is* the fixture root. Correctness is the more specific claim and is verifiable from `scripts/vcs-common.sh:8-18`. **Recommendation**: verify empirically with a `bash -x` trace, record the observed spawn count rather than one implied by depth, and then state depth-insensitivity as a positive reproducibility property for the linux hand-off — which is the stronger result if it holds.
- **Ratio gate vs absolute budget**: Performance and Correctness both want an absolute `median(G)`/`p90(G)` ceiling as the primary criterion, on the grounds that `B` is a deleted artefact recovered from `cf42441e2aad-` whose live dependency is in 0199's scope, so nothing can ever re-run the ratio as a regression gate; the plan declines the absolute route without recording why, though 0205 named it. Against that, 0169's inherited wording is a ratio, and discharging it requires one. **Recommendation**: adopt both — an absolute budget as the re-runnable primary criterion, with `G ≤ 1.4 × B` retained as the recorded historical comparison that discharges 0169.
- **Threshold rigour vs decidability**: Performance and Correctness converge on the same fix from opposite directions — either gate at 1.3 and pre-register n at the sizing rule's half-width-0.005 value (~1,700 pairs, ~3 minutes, a budget the plan already commits to for escalation), or keep 1.4 and delete the decidability rationale, leaving only the structural and absolute arguments, which are value-independent but do not distinguish 1.4 from 1.3. **Recommendation**: the first. It costs three minutes and removes the plan's most exposed reasoning.
- **Harness as committed task vs throwaway**: Architecture and Documentation want the pre-flight capture and abort checklist pulled *inside* the module as a context manager, so committed code stops depending on uncommitted scripts and the linux hand-off genuinely runs a task. Portability adds that the pinned `PATH` must become per-OS data rather than a darwin constant, or the hand-off patches source anyway. Against that, more committed surface in a namespace no CI lane exercises is more rot. **Recommendation**: pull them in, and pay for the rot risk with a cheap `n=2` self-test wired into `test:unit:tasks` — which Phase 2's manual verification already performs ad hoc.
- **Cleanup of the trust-chain alarm log**: Safety wants log growth promoted to a branch-5 invalidation trigger and the file left strictly append-only, since any appended line *is* a `fail_integrity` or an engaged override, and pid-based attribution is unreliable in a repo already bitten by pid reuse. The plan wants attributable lines removed to leave the operator's log clean. **Recommendation**: append-only. Record the lines verbatim in Validation Results, invalidate the session, escalate — never edit an alarm log.

### Findings

#### Critical

- 🔴 **Correctness / Safety / Standards / Architecture**: The baseline recovery command writes to the exact location the same section forbids
  **Location**: Phase 3, §1 "Recover the baseline's subject"; Abort checklist item 1
  The snippet is `jj file show -r cf42441e2aad- hooks/vcs-guard.sh > bin/.tmp-vcs-guard-baseline` plus `chmod +x`; three paragraphs later the plan states the baseline must be parked in temp dir `T` because "`bin/` … is the launcher's **live cache root**, and parking an unreviewed executable under the `store::TEMP_PREFIX` namespace adds an entry to the very directory whose `cache::find` scan the budget accounts for". Both hazards verify — `store::TEMP_PREFIX` is literally `".tmp-"` (`cli/store/src/lib.rs:24`) and the cache root is `${plugin_root}/bin` (`bin/accelerator:201`). The abort checklist and two Phase 3 success criteria name the forbidden path, so under the `T` arrangement they assert absence of a path never created, while `T` — holding an executable copy of a deleted VCS guard beside a symlink into the live `scripts/` — is covered by no cleanup item at all.

- 🔴 **Documentation / Correctness / Standards**: 0189's acceptance-criterion numbering is off by one and cites a criterion 13 that does not exist
  **Location**: Phase 1 §1 and §3; Phase 4 §2; Desired End State
  `meta/work/0189-…md` has exactly twelve `- [ ]` boxes; the latency criterion is **#10** (`:197-199`), the recording criterion **#11** (`:200-202`), `mise run` **#12** (`:203`). The plan calls the latency criterion 11, the recording criterion 12, instructs Phase 1 to tick "1 to 10, 12 … and 13", and simultaneously says "twelve" in two other sections. Executed literally, Phase 1 ticks the unmeasured latency criterion, Phase 4's branch-1 tick lands on the recording criterion, and the phantom 13 has no referent.

- 🔴 **Test Coverage / Architecture / Correctness / Standards**: The envelope-normaliser specification cannot be implemented as written
  **Location**: Phase 2 §1 (envelope normalisation); Phase 2 Manual Verification; Phase 3 §4
  The plan requires the port to "match" `cli/vcs-cli/tests/guard_decision_table.rs:99-141` *and* to pin that empty stdout normalises to something distinguishable from an allow. The Rust function returns `("allow","")` for empty stdout at `:127-129` — the same conflation the plan condemns in `generate_decision_table.py:160` — has no branch for the legacy `{"decision","reason"}` shape that `B` emits (unrecognised envelopes are an `Err`), labels anything carrying `permissionDecisionReason` as `block` without checking `permissionDecision == "deny"`, and reads `systemMessage` at the top level while the shell's warn shape sits under `hookSpecificOutput`. A faithful port aborts on the first `B` sample; a compliant one diverges from its stated oracle. The `warn` branch is omitted from the plan's description entirely, despite Phase 3's fixture hazard being precisely that a colocated fixture emits warn.

- 🔴 **Correctness / Performance**: The argument that selects 1.4 over 1.3 is refuted by the plan's own sizing rule
  **Location**: Desired End State (threshold reframing); Phase 1 §1
  The stated reason for the looser end of the 1.3–1.5 band is that "at 1.3 the margin from the CI upper bound is 0.0101 against a half-width of 0.0119, so the verdict would be decided by noise". The arithmetic is right, but half-width is a function of a freely chosen n, and the plan's own rule `n = n₀ × (h₀/target)²` gives ~1,700 pairs for half-width 0.005 — roughly three minutes at the plan's own ~106 ms per pair, exactly the budget branch 3 already commits to. At that n, 1.3 is decidable with ~3.7 half-widths of margin against 1.2813. The only argument claiming to select 1.4 non-arbitrarily therefore does not hold, leaving the relaxation justified solely by structural and absolute arguments that do not distinguish 1.4 from 1.3.

#### Major

- 🟡 **Portability / Performance / Correctness**: The criterion binds a host configuration no CI lane and no stock macOS install provides
  **Location**: Phase 1 §1; Current State Analysis (digest-backend table)
  `bin/accelerator:272-278` selects the backend by bare `command -v sha256sum` with no override seam; the only darwin lane is a stock `macos-latest` runner with no coreutils install anywhere in the tree. The plan's own table predicts the `shasum`-only configuration at `G` ≈ 59.2 ms and ratio ≈ 1.79 — above every threshold in the stated band — and leaves it with no criterion, routed to a 0191 that Phase 4 simultaneously declares no longer a latency-gate co-requisite and which caps out around 12 ms on that backend.

- 🟡 **Correctness / Test Coverage**: The taxonomy has a hole after escalation, and the classifier's stated inputs cannot select four of six branches
  **Location**: Phase 3 §6; Phase 2 §1 (outcome classifier)
  Branch 3 escalates once then re-classifies "into branch 1, 2 or 4", but branch 4 requires half-width ≤ 0.005; if the escalated run's dispersion is worse the interval straddles 1.4 above that half-width, matching only branch 3, whose escalation is spent. Separately the classifier is specified as taking "the interval bounds and a threshold", which cannot distinguish 3 from 4 (needs escalation state), cannot select 5 (validity) and cannot select 6 (budget) — so the promised "exactly one branch selects for any interval" is not a writable test, and branch 5 in particular has no coverage at all.

- 🟡 **Safety / Correctness**: The abort checklist asserts rather than remediates, and its trap handler runs a multi-minute cargo pass
  **Location**: Abort checklist
  Every item bar 5 is phrased as a post-condition ("do not exist", "matches its pre-flight state", "is green"), and nothing is assigned the job of deleting the baseline or restoring the marker; at the moment a trap fires the artefacts *do* exist, so item 1 fails first and items 5–6 never evaluate. Item 6 additionally invokes `mise run cli:check` from `trap … EXIT INT TERM`, so an operator Ctrl-Cing twice to escape the slow handler kills it before anything is restored — and `cli/` is a vestigial referent, since no phase of this plan mutates that workspace.

- 🟡 **Test Coverage / Architecture**: The validity gate is never proven to fire, and every Phase 3 "automated" criterion is self-certified by untested code
  **Location**: Phase 2 §1; Phase 3 §4-5 and Automated Verification
  Phase 2 excludes the driver, fixture construction and provenance capture from unit testing, yet all five Phase 3 automated criteria are assertions inside that code. Nothing makes the gate demonstrate that it *rejects* a bad sample — the exact failure the plan identifies (`swallow_under_fail_safe` + `handle_dispatch_error` exit 0 with empty stdout, recording a spuriously low latency, i.e. biased toward passing). The driver is also not thin: it owns the `ACCELERATOR_*` key filter, the CPU-count rung chain, the `realpath`-canonicalised ceiling, the backend `PATH` switch and a four-artefact inode witness, all of which fail by corrupting rather than crashing.

- 🟡 **Correctness / Performance**: Raw medians are labelled "conservative" when the plan's own algebra shows them lenient, and the ten-half-widths claim is statistic-dependent
  **Location**: Phase 3 §2 (instrument floors); Phase 1 §1
  `(G−c)/(B−c) > G/B` for `G > B > c > 0` is correct, but for a gate of the form `ratio ≤ threshold` a statistic biasing toward passing is the *lenient* choice, not the conservative one. The policy was conservative in 0205, whose verdict was fail; 0189 expects a pass, so it now selects the most favourable statistic. On 0205's figures the bash-floor-subtracted ratio is 1.358 — ~3.5 half-widths from 1.4, not ten — and would fail 1.3 outright. Phase 1 bakes "on raw (not floor-subtracted) medians" into 0189's permanent criterion on the strength of the inverted label.

- 🟡 **Documentation / Standards / Correctness**: Every 0189 stale-passage anchor and both `sha256_file` call-site anchors are stale
  **Location**: Phase 1 §2; Current State Analysis; References
  The five quoted passages resolve at `:127`, `:198-199`, `:246`, `:305-306` and `:317`, not the cited `:112-113` / `:168-170` / `:197-203` / `:256-258` / `:268-270` — drift of 15 to 49 lines, and the cited `:197-203` now points at the acceptance criteria Phase 1 §3 separately edits. The `sha256_file` call sites are at `:291` and `:295`, not `:288` and `:291`, which is what the plan's cited source (0205) records. The plan's own instruction is "enumerate by quoted text, not line number" — the anchors should simply go.

- 🟡 **Documentation**: After Phase 1, 0189 still asserts `G ≤ 1.1 × B` in three unenumerated passages
  **Location**: Phase 1 §1-2
  The retraction set is keyed on the *release gate*, not the threshold, so `1.1` survives in the Requirements bullet (`:124-128`), the Assumptions bullet (`:269-271`, "0169's Phase 10 definition … is still the right shape … If the epic has since revised the threshold, this item follows the epic" — directly falsified by this plan, and its own escape clause has now fired) and Drafting Notes (`:303`). 0189 emerges with a criterion reading 1.4 and its Requirements and Assumptions reading 1.1.

- 🟡 **Documentation**: 0205 is closed `done` with eight unticked criteria and a stale Blocks edge
  **Location**: Phase 1 §6
  The step sets `status: draft` → `done` and appends two corrections, but says nothing about 0205's eight unticked acceptance criteria (`:175-195`), all discharged by its own Spike Outcome / Findings / Cleanup Evidence sections, nor about its Dependencies line "Blocks: `plan:2026-08-11-0189-warm-dispatch-latency-measurement`, which cannot specify its measurement until SQ-1 to SQ-4 are answered". This reproduces verbatim the failure the plan's Current State Analysis opens by condemning.

- 🟡 **Safety / Correctness**: The live trust root is never hashed, and the repo-state gate is scoped to `cli/` only
  **Location**: Pre-flight item 1; Abort checklist items 3 and 6
  Pre-flight hashes the key via `jj file show -r @`, but `-r @` reads the auto-snapshotted working-copy commit, so the committed-versus-working-copy framing does not describe what the check does; meanwhile the file the bootstrap reads (`bin/accelerator:165`) and `build.rs` embeds is the working copy. Item 6's `jj diff --summary cli/` cannot see a modification to `keys/`, `bin/accelerator`, `hooks/` or `scripts/` — so the plan's most-emphasised safety property is verified against neither the artefact in use nor the paths the measurement's validity depends on. What actually detects a prior substitution is comparison against 0205's published `0f3fe9a9…`, which the plan quotes but does not make the mechanism.

- 🟡 **Safety**: A cache or verification anomaly makes every sample re-fetch the launcher, detected only after the run
  **Location**: Phase 3 §4; Phase 3 §6 branch 3
  `FetchVerifyCacheResolver::resolve` (`resolve/mod.rs:198-211`) self-heals on any cache-hit re-verification failure by calling `fetch_verify_store`, re-downloading the ~8 MB asset. The inode/mtime witness is asserted only *after* the run, and branch 3's escalation implies ~1,700 pairs across two backend passes. One corrupt entry, a mid-run eviction or a key mismatch turns an offline benchmark into thousands of consecutive fetches — tens of gigabytes of egress and a nonsense ratio — with nothing detecting it until the end.

- 🟡 **Safety**: Growth of the trust-chain alarm log is treated as cleanup, not as an invalidating integrity event
  **Location**: Abort checklist item 5; Phase 3 §6 branch 5
  `.accelerator-unverified.log` is written only by `fail_integrity` and the dev-override exec (`bin/accelerator:58-68`, `:246-249`), so any line appended during the run *is* a trust-chain failure or an engaged override — yet branch 5's triggers omit log growth, and item 5 treats appended lines as something to attribute and remove. Attribution is unspecified and unreliable: the record format is `timestamp pid=$$ message`, the pid belongs to the bootstrap subprocess, the harness is never asked to capture those pids, and this repo has already been bitten by pid reuse.

- 🟡 **Safety**: Removing the cache-hit sha256 costs the name-to-content binding, not only a diagnostic
  **Location**: Phase 4 §4 (warm-dispatch verification cost follow-up)
  The provenance reasoning is sound — the digest comes from the entry's filename (`cache.rs:57`) and `keys.verifies` binds the bytes independently (`keys.rs:62-69`). But minisign signs only bytes; nothing in the signature binds the asset *name or version*, while `cache::find` selects by the `{name}-{version}-` prefix. Today the name-derived comparison is what rejects an entry whose filename disagrees with its content, so removal turns a stale copy or a botched cache edit into silent wrong-version execution rather than a clean `ChecksumMismatch`.

- 🟡 **Safety**: The concurrent-session precondition has no verification mechanism, and the driving session is itself one
  **Location**: Phase 3 §5
  "No other Claude Code session is active against this plugin root" is asserted with no check specified, is not inspectable from the environment unlike its list-mates, and cannot exclude a session that starts mid-run. The plan is also executed *by* a session whose SessionStart and PreToolUse hooks dispatch `bin/accelerator` against this same plugin root — so the precondition protecting the inode witness and the log check is unenforced, and its failure is indistinguishable from tampering.

- 🟡 **Performance**: A ratio gate against a deleted baseline is not re-runnable, and the absolute-budget alternative is declined without reason
  **Location**: Desired End State ("The `B`/`G` work asymmetry is accommodated, not resolved")
  The plan accepts 0205's conclusion that a ratio is only meaningful between variants doing the same work, then keeps the ratio and moves the number. 0205 named "a threshold expressed as an absolute budget, or as a ratio against a like-for-like baseline" as the defensible reframings; both are declined and only the second is explained. Since `B` is recovered from `cf42441e2aad-` and its live dependency is in 0199's scope, nothing can re-run the criterion — so a future regression in warm dispatch will not be caught, and the milliseconds users actually feel are never bounded.

- 🟡 **Performance**: The two digest-backend arms are batched, which is the confound interleaving exists to prevent
  **Location**: Phase 3 §2 ("Both digest backends")
  The plan interleaves `B` and `G` because "batching cannot alias drift onto the difference", then runs the two backends as two sequential whole sequences and uses their difference as a measured quantity. Drift is not hypothetical: each `G` sample hashes ~10.7 MB, so 300+ samples drive real thermal load, and the load is variant-specific — `B` hashes nothing — so `B`/`G` interleaving does not cancel a thermal effect that inflates only `G`. `pmset -g therm` is recorded with no policy for what a throttle observation means.

- 🟡 **Performance**: The backend delta does not isolate the two `sha256_file` calls
  **Location**: Phase 3 §7
  The delta yields `2 × (shasum − sha256sum)` ≈ 16.9 ms, not the ~7.1 ms absolute cost in the gating configuration. Recovering the absolute sub-term requires 0186's 3.55 ms from a different session, so the uncross-checked 30% of `G` is closed by a borrowed figure rather than an in-session isolation — while the plan reports it as partially closing the gap, which will overstate the cross-checked fraction in the permanent record.

- 🟡 **Performance**: The composition-budget band contradicts the plan's own negative-residual rule and cannot detect the effects under discussion
  **Location**: Phase 3 §7
  0205's term set was measured at load 19 and is compared against a quiet-host `median(G)`; if a quiet host lowers `G` toward the ~38–40 ms its 1.16-ratio run implies, the residual against a fixed 40.99 ms sum goes *negative* while remaining inside ±8% — yet the plan declares a negative residual evidence of double-counting. Separately ±8% of `G` is ±3.38 ms, wider than either lever the plan costs and declines (4.49 and 2.48 ms), so the check cannot detect a term moving by as much as the decisions being made.

- 🟡 **Correctness / Performance**: The `dirname` spawn-count provenance is vacuous
  **Location**: Current State Analysis; Phase 3 §3
  `find_repo_root` (`scripts/vcs-common.sh:8-18`) initialises `dir="$PWD"` and tests `-e "$dir/.jj"` *before* calling `dirname`; Phase 3 sets the subprocess cwd to the fixture root, where `jj git init` created `.jj`. The loop matches on iteration one and spawns `dirname` zero times at any depth — so a recorded field is guaranteed zero, and the surviving half of the fixture-choice rationale (depth sensitivity, "roughly 1 ms per spawn") does not exist. See the Tradeoff Analysis: Portability reads this the opposite way.

- 🟡 **Portability / Correctness / Safety**: "Remove the fast backend from PATH" is neither isolable, portable, nor positively asserted
  **Location**: Phase 3 §2
  No mechanism is given, and `sha256_file` has no backend seam (unlike `scripts/hash-common.sh`, which honours `_HASH_BIN`), so the only lever is `PATH` — and dropping the directory holding `sha256sum` drops its neighbours: `/opt/homebrew/bin` also supplies `jj`, `jq` and GNU `grep`/`sed`/`awk`, while on linux `sha256sum` sits in `/usr/bin` alongside every tool `B` spawns, so the second arm is not constructible there at all. Nothing asserts that no `sha256sum` remains reachable under the second `PATH`; if one survives, the two `G` values collapse, the ~1.79 prediction records as "did not hold" for a spurious reason, and the §7 isolation evaluates to zero. The plan should also state explicitly that the arm is produced by `PATH` construction only, never by moving or chmod-ing a system binary — a mutation with no entry in the abort checklist.

- 🟡 **Portability**: The committed harness bakes in a host-specific `PATH`, so the linux hand-off must patch it rather than run it
  **Location**: Phase 2 §2; Phase 3 §5; Phase 4 §4
  Phase 2's stated value is that the hand-off "runs a task instead of retyping a script", but the pinned `PATH` is a darwin-and-homebrew constant and the plan only says the hand-off "constructs an equivalent". Nothing externalises it as a per-OS default or a documented input, so the hand-off modifies harness source on a branch — reintroducing the per-platform divergence Phase 2 exists to eliminate.

- 🟡 **Portability**: The provenance record omits the tools that constitute `B`'s entire cost
  **Location**: Phase 3 §5
  The plan establishes `B`'s cost as "bash startup plus roughly fifteen `jq`/`grep`/`sed`/`awk`/`cat`/`timeout` pipeline spawns", then records only `jj`, `git`, `bash`, `realpath`, `jq` and the digest backend. On a homebrew-first `PATH` those spawns resolve to GNU tools; on stock macOS to BSD ones with different startup costs, and `timeout` is absent from the macOS base system entirely. The gate's denominator therefore depends on an unpinned, unrecorded tool flavour, and the hand-off would read a GNU-versus-BSD difference as a platform one.

- 🟡 **Portability**: No precondition that the working tree's version has a published signed release
  **Location**: Phase 3 §5; Phase 4 §4
  The warm path is only reachable if a launcher for `plugin.json`'s version exists or can be fetched (`bin/accelerator:138-141`, `:349`). The tree is at `1.24.0-pre.37` while the plan's evidence covers `pre.36`/`pre.35`, and this workspace's `bin/` holds only `pre.20`/`pre.21`/`pre.30`. The preconditions require a warm-up dispatch but never assert a signed asset exists for the current version, so on any unreleased checkout — including the hand-off host — the run fails as an opaque bootstrap abort rather than a named unmet prerequisite.

- 🟡 **Architecture / Documentation**: `measure:*` is committed with no owning lane and no operator documentation
  **Location**: Phase 2 §2; Phase 4 §4

### Performance

**Summary**: The instrumentation design is unusually careful — interleaved pairs, a seeded paired bootstrap, a pre-registered taxonomy with an explicit no-optional-stopping rule, per-sample validity gating against the fail-safe swallow, and a corrected shell-baseline cost model. The weaknesses are in the *gate*: 1.4 is justified by a noise-decidability argument the plan's own sizing rule defeats; the raw-medians policy is inherited from 0205 with the verdict's sign flipped, so it now biases toward the expected pass; and the ratio statistic 0205 called not-meaningful is retained against a baseline no longer in the tree, so the criterion can never re-run as a regression gate. The configuration most users are likely on is placed outside the gate with nothing absolute bounding it, and two budget claims — that the dual-backend delta "isolates the two `sha256_file` calls" and that ±8% tests closure — do not hold arithmetically.

**Strengths**: the right instrument for a ~40 ms quantity (interleaving with within-pair alternation, one Python process, explicit rejection of per-call interpreter startup); a dispersion-aware gate statistic with n/min/median/p90/IQR and `p90(G)/p90(B)`; pre-registered taxonomy with one permitted escalation and an explicit optional-stopping prohibition; the validity gate aimed at the spuriously-low failure; the inode/mtime branch witness; the verified `B` cost-model correction and the identification of 0205's load claim as unsupported by its own non-monotone points; `measure:*` kept out of the CI mirror; the committed harness turning a thrice-hand-rolled transcript into a one-generation cost; positive cleanup assertions.

**Findings**:

- **major / high** — The 1.4-over-1.3 rationale evaporates under the plan's own sizing rule; at half-width 0.005 (n ≈ 1,700, ~4 minutes, already budgeted) 1.3 has ~3.7 half-widths of margin. *Location: Desired End State; Phase 1 §1.* Either gate at 1.3 with n pre-registered, or keep 1.4 justified only structurally/absolutely.
- **major / high** — The no-subtraction policy was conservative in 0205 (verdict: fail) and is anti-conservative here (expected: pass). *Location: Phase 3 §2.* `true`-floor-subtracted = 1.297; bash-floor-subtracted = 1.358 — ~3.5 half-widths from 1.4, not ten, and failing 1.3 outright. Report all three with intervals and accept on the worst.
- **major / high** — The ratio is kept against a deleted baseline whose live dependency is in 0199's scope, so nothing can re-run it; 0205's absolute-budget alternative is declined unexplained. *Location: Desired End State.* Make an absolute `median(G)`/`p90(G)` budget primary and keep the ratio as the historical comparison.
- **major / high** — The fallback backend (predicted `G` ≈ 59.2 ms, p90 ≈ 63 ms, ratio ≈ 1.79) has no criterion; 0186 declined to call `/sbin/sha256sum` a darwin fact, and 0191 caps at ~12 ms leaving `G` ≈ 47 ms. *Location: Current State Analysis; Phase 3 §2.* Add an absolute non-ratio criterion for it and record `command -v sha256sum` on both CI lanes to quantify the binding population.
- **major / high** — The two backend arms are run as sequential whole sequences and their difference used as a measured quantity — the exact between-batch comparison rejected within a pair. *Location: Phase 3 §2.* Each `G` sample hashes ~10.7 MB, so thermal load is real and variant-specific, and `B`/`G` interleaving cannot cancel an effect inflating only `G`. Interleave all four arms or run ABBA; add a first-third/last-third drift diagnostic with a pre-registered invalidation band.
- **major / high** — Two problems with closure: the term set was measured at load 19 and compared against a quiet-host `G`, so a lower `G` drives the residual negative while staying inside ±8% — which the plan declares evidence of double-counting; and ±3.38 ms is wider than either lever it costs (4.49, 2.48 ms). *Location: Phase 3 §7.* Re-measure terms in-session, tighten to ±1.5 ms, make a negative residual an automatic re-measure.
- **major / medium** — The delta yields `2 × (shasum − sha256sum)` ≈ 16.9 ms, not the ~7.1 ms absolute cost; recovering it needs 0186's 3.55 ms from another session, so the 30% gap is closed by a borrowed figure. *Location: Phase 3 §7.* Measure the substitutions directly in-session and use the delta as the cross-check.
- **minor / high** — Neither quietness witness carries a decision rule; 0205's floors were 15% and 22% above 0186's and were still called nearest. *Location: Phase 3 §5.* Pre-register numeric bounds, cap recorded retries, treat a breach as branch 5.
- **minor / high** — The 0191 saving is quoted three ways (2.48 ms measured; "two ~3.55 ms calls into one"; "order of magnitude" for ~4–5×), and the fallback saving is a projection 0191 itself flags as unconfirmed on `shasum`. *Location: What We're NOT Doing; Phase 1 §4; Phase 4 §3.*
- **minor / medium** — The depth-derived `dirname` spawn count is zero regardless of depth, and the useful property — depth-insensitivity for the hand-off — goes unstated. *Location: Current State Analysis; Phase 3 §3.*
- **minor / medium** — The empty pure-jj fixture is `G`'s best case while `B` is state-independent; 0188 bounds the bias at ~±1 ms (4.81 vs 4.03 ms all-queries; 2.80 vs 3.58 ms single). *Location: Phase 3 §3.* Cite it as the recorded bound and note the limitation.

### Safety

**Summary**: Blast radius is one developer's plugin root — the live launcher cache, staged verify shim, trust-chain alarm log and release public key — plus the meta corpus. Safety instincts are unusually good: pre-flight keyed on a published digest, positive-absence assertions because everything involved is gitignored, an explicit refusal to truncate unattributable trust-chain records, and no dev-override route. The gaps are in the recovery mechanism rather than the intent: the checklist detects rather than remediates and puts a multi-minute cargo run inside an interrupt trap; the baseline location contradicts itself so the scratch tree holding an unreviewed executable and a live-`scripts/` symlink is covered by no cleanup assertion; the trust-root and repo-state checks are scoped to miss a working-copy substitution; and the ~1,700-dispatch worst case can trigger the launcher's self-healing re-fetch on every sample with detection deferred to after the run.

**Strengths**: pre-flight compared against a published literal digest; positive absence assertions with the gitignore reasoning; refusal to blind-truncate the alarm log; the trust-root immutability reasoning (`bin/accelerator:165` + `build.rs`, and `keys:generate` force-overwrites); no dev-override route at all; the validity gate targeting the empty-stdout swallow and rejecting the shell-only normaliser; branch 5 failing safe rather than open; the fixture outside the plugin root and any jj workspace with `git.colocate=false` pinned and the decision shape probed; dated notes rather than rewrites across closed documents; `measure:*` out of the CI mirror with a guard.

**Findings**:

- **major / high** — The checklist detects but does not remediate, and its trap runs `mise run cli:check`. *Location: Abort checklist.* Removal is only ever attributed to the fixture's context manager, which does not cover the manually recovered baseline; no failure semantics are defined, so an early assertion failure leaves items 5-6 unevaluated, and a second Ctrl-C to escape the slow trap kills the handler before anything is restored. - **major / high** — Baseline placement contradicts itself and the scratch tree is uncovered. *Location: Phase 3 §1.* If `T` is the real arrangement, item 1 and the success criterion assert a path never created and pass trivially, while `T` — an executable copy of a deleted security-relevant hook beside a symlink into the live `scripts/` — is named nowhere ("the fixture root" is a different directory). ### Architecture

**Summary**: Rigorous about evidence, provenance and the epistemics of its own threshold change, with well-targeted corpus reconciliation. Architecturally the load-bearing seam is drawn in the wrong place: the TDD'd phase carries almost none of the gate's validity risk, while the untested "thin driver" owns preconditions, per-sample validity, the inode/mtime witness, fixture construction and cleanup. Two further structural problems: the committed harness depends on a throwaway abort script, so it cannot run self-contained — defeating Phase 2's stated justification — and it introduces a third hook-envelope normaliser in a third language with contradictory conformance requirements and no sync mechanism, in a repo that otherwise enforces exactly this kind of cross-surface duplication with dedicated lint guards.

**Strengths**: the outcome-keyed closure guard avoiding a gate born discharged; the self-corrected `B` cost model with its consequences propagated; positive cleanup assertions with the right failure model for gitignored side effects; the work asymmetry named as accommodated-not-resolved and the post-hoc relaxation recorded as a deviation; the explicit work-item-authoritative / plan-appendix relationship; the pre-registered six-branch taxonomy with a no-optional-stopping rule and boundary disjointness tests.

**Findings**:

- **major / high** — The pure/thin seam isolates the low-risk half. *Location: Phase 2 §1; Phase 3 §4-5.* Validity lives in the driver: the `ACCELERATOR_*` scan, the pre-sampling probe, the per-sample gate, the four-artefact witness, dual-backend `PATH` pinning, the CPU rung chain, and fixture/cleanup lifecycle. A defect there yields a plausible ratio — the one failure mode the plan is built to prevent — while the tested bootstrap CI would be wrong obviously. Introduce a runner port and an environment/filesystem probe port so those become pure functions over recorded observations, leaving only `subprocess.run`, `os.stat` and temp-dir invocation untested.
- **major / high** — Third normaliser, contradictory conformance, no sync mechanism. *Location: Phase 2 §1.* Three implementations of one protocol mapping in two languages, none a shared source of truth (the Rust one lives in a `tests/` target and is not importable). The requirements are incompatible, since `:127-128` returns `Ok(("allow", String::new()))` for empty stdout. And the repo already enforces cross-surface duplication mechanically (`tasks/lint/store_duplication.py`, `lint:vendor-shims:check`, `lint:dispatch-coherence:check`), so a third uninstrumented copy diverges from an established pattern without acknowledgement. Resolve the contradiction explicitly, then give the duplication one owner — a shared helper, or a guard test pinning the envelope shapes so a `hooks.rs` change breaks a test rather than a future measurement.
- **major / high** — The committed harness depends on a throwaway script, so the hand-off still re-authors code. *Location: Abort checklist; Pre-flight; Phase 2 Overview.* Committed code calls an uncommitted dependency it cannot run without, and the uncommitted part is where the safety-critical logic lives. Pull pre-flight and abort/restore inside the module as a context manager with signal handling, keeping only the escalate-don't-truncate policy as an explicit refusal path.
- **major / medium** — The stated dependency graph is incomplete, and Phase 3 is not mergeable in the same sense. *Location: Implementation Approach.* Phase 3 depends on Phase 1 too (every branch is expressed against 1.4), so the real graph is `1 → 3`, `2 → 3`, `{1,3} → 4`; and Phase 3 produces no reviewable change beyond this plan's Validation Results. Restate the graph and label Phase 3 a one-shot recorded session.

### Assessment

The revision is a genuine improvement on pass 1 — every critical closed, the citation hygiene repaired wholesale, and the corpus instructions turned from stale anchors into recorded searches. Three of the four decisions taken between passes were sound in direction.

The problem is that the fourth structural change — restructuring one ratio criterion into a five-cell primary/historical table — was made without carrying the taxonomy, the sizing rule, the statistic and the classifier signature along with it. Every one of the two new criticals and eight of the new majors trace to that single gap. The second cluster, around the harness's new self-test and teardown, is smaller but sharper: five lenses independently found the same lane-hermeticity breach, and the guard designed to prevent it cannot see it.

Two findings deserve the author's attention before any further editing, because they are decisions rather than defects. First, the floor-policy choice made between passes has the unintended consequence that **branch 1 is unattainable at the chosen sample size** — the gate as specified cannot pass on the plan's own numbers. Second, the **1.3–1.5 band has no recorded provenance anywhere in the corpus**, which leaves the stated mitigation for a post-hoc threshold relaxation unauditable.

Recommended sequence: fix the taxonomy/criterion coherence cluster first as one edit (it is the root of most majors), then the self-test placement and the teardown artefact inventory, then the corpus-sweep completeness items, then the minors.
