# 0121: Topic Research Skillset

**Kind**: Epic
**Status**: Ready
**Priority**: High
**Author**: Toby Clemson

## Summary

As an Accelerator user, I want a skillset that performs broad-and-deep research on arbitrary external subjects — concepts, domains, technical fields, expert knowledge — so that I can quickly build a thorough, citation-backed knowledgebase on a subject, iteratively deepen or widen it, and consult it afterwards.

This epic delivers a `research-topic` skill implementing an iterative, parallel, multi-agent deep-research loop with seven subcommands split into two groups: **build** (`brief` → `outline` → `conduct` → `synthesise` → `finalise`), and **consume** (`ask`, `report`). The build loop authors a brief for a subject, outlines the focus areas to research, conducts a round of parallel research producing one immutable finding per focus area, synthesises the findings into a whole-corpus dossier, and finalises the subject when it has been researched enough. The consume verbs read the accreted corpus: `ask` answers a question in conversation, `report` writes a formal report — and both can surface coverage gaps that feed a subsequent `outline`. Findings accrete as immutable documents under `meta/research/topics/<slug>/`. Critically, it is built on **reusable infrastructure** — a generic `researcher` agent specialised at spawn time along two axes (a source profile naming the source family and APIs it draws on, and a focus — the focus area's question it researches), the same injection pattern as the `reviewer` agent, plus templates and a stable artifact contract — so later, more specific research skills (competitor research, technical-topic research, an ideation skillset) can be layered on top without rebuilding the engine. New artifacts are surfaced in the visualiser library.

## Context

Accelerator today can research a codebase but not the world outside it. `research-codebase` and `research-issue` both stop at the repository boundary, so when a piece of work turns on external knowledge — an unfamiliar domain, a protocol, a body of prior art, a technology being evaluated — that research happens ad hoc in conversation and dies with the session. Nothing lands in `meta/`, nothing is citable, nothing accretes, and the next person to need the same understanding starts over. This epic closes that gap: a durable, citation-backed knowledgebase per subject that later work items, plans and ADRs can reference, that deepens on demand rather than being rebuilt, and that can be consulted directly through `ask` and `report`.

The design is grounded in a survey of existing deep-research systems:

- **Sagan plugin** (`robertbagge/claude-sagan-plugin`) — the closest model: three skills (`/create-brief`, `/deep-research`, `/synthesize`) run one round per invocation, fanning out one parallel agent per topic, with immutable per-topic files, an append-only round log in the brief, and a synthesis rewritten each round. `/create-brief` enumerates the initial topics with the user; `/deep-research` both researches a round *and* proposes+appends the next round behind an interactive gate, then stops. Re-invocation detects the first round with missing files and fills only the gaps. An "anti-changelog" output rule keeps the accreted corpus reading as a single dossier.
- **Anthropic's multi-agent research system** — the orchestrator/sub-agent architecture, the effort-scaling rubric (1 agent for simple, 2–4 for comparisons, 10+ for complex), the four-part sub-agent brief (objective / output format / tools & sources / boundaries) as the main defence against duplicated work, "start wide then narrow", and citation as a dedicated final pass. The lead agent saves its plan to memory before executing — a plan/execute separation, though internal and not user-editable. Caveat: multi-agent runs cost ~15× the tokens of a chat, so depth/breadth must be controllable.
- **dzhng/deep-research** — the cleanest depth × breadth parameterisation (breadth = queries per level; depth = recursion levels; breadth halves each level to narrow the tree). It keeps two distinct question-generators — `generateFeedback` (user-facing, asked once up front) and `followUpQuestions` (machine, inside the recursion) — but never pauses for the user between levels.
- **superpowers `/brainstorming`** — a strong convergence/approval-gate pattern, but thin on divergence; informs a later (out-of-scope) ideation skillset rather than this epic.
- Plus academic toolchains (`imbad0202`, `lingzhi227`) for source-verification and reputation-tier ideas, and the `DavidZWZ/Awesome-Deep-Research` landscape.

**Design divergences the survey motivated.** Two shape this epic. First, none of the surveyed systems surfaces a *user-editable plan* or a research step separate from the research itself — Sagan folds propose-next-round into `/deep-research` behind a gate; dzhng and Anthropic keep the between-rounds loop machine-autonomous. This epic instead makes the plan/execute split explicit and user-editable: `outline` decides the focus areas (a human can edit the result) and `conduct` executes them. That matches Accelerator's own `create-plan` → `implement-plan` idiom and removes the "dangling proposed round" wart that a fold-in creates. Second, none surfaces read-only consumption of the accreted corpus; this epic adds `ask` and `report`, closing a build → consult → discover-a-gap → refine loop that the reference systems stop short of.

This work conforms to existing Accelerator conventions: artifacts under `meta/research/` with YAML frontmatter and a `type` discriminator; 3-tier template override; per-skill `instructions.md`/`context.md`; agent overrides via config; and the subcommand-dispatch pattern already established by `skills/config/configure/SKILL.md`. The grouping directory is `meta/research/topics/` (sibling to `codebase/`, `issues/`, `design-inventories/`, `design-gaps/`), chosen to read as a subject-typed peer of the existing research categories.

The area is greenfield — no overlapping work items exist; the nearest is `0056` (restructure `meta/research/codebase/` into subject subcategories), which explicitly lists external research as a non-goal.

## Requirements

### High-level goals and themes

1. **Reusable research infrastructure** — a generic `researcher` agent specialised at spawn time along two orthogonal axes: a **source profile** (the source family and APIs it draws on — web, academic) and a **focus** (the focus area's question it researches). Only `conduct` spawns researchers; `synthesise` and `report` run inline in the skill over the immutable findings and spawn nothing. Plus research templates and a stable brief / outline / finding / synthesis / report artifact contract. This is the foundation that future, more specific research skills consume; `research-topic` is its first consumer.
2. **The `research-topic` skill** — seven subcommands on the `configure` dispatch pattern, in two groups: **build** (`brief` / `outline` / `conduct` / `synthesise` / `finalise`) and **consume** (`ask` / `report`).
3. **Iterative knowledgebase accretion** — immutable per-focus-area findings, an outline that logs focus areas per round with per-item progress, a wholesale-rewritten synthesis, and gap-detection so re-invocation only researches outstanding focus areas.
4. **Multi-source research** — web and academic sources, realised purely through injectable profiles that tag every source with a **reputation tier**. "Reputation tier" is the single term this epic uses for source-quality ranking, and it is reputation-only: the tier reflects the standing of the publishing venue or outlet, not any assessment of a claim's correctness. External sources only (no codebase/internal); source families beyond web and academic are out of scope (see Dependencies).
5. **Read-only consumption** — `ask` (answer a question in conversation from the corpus) and `report` (write a formal report from the corpus); both are read-only over the findings and synthesis, and both may propose a new focus area to a subsequent `outline` when coverage is thin, applied only on user confirmation.
6. **Configuration & override surface** — depth/breadth tunable at project/user config and per-invocation, plus template override and per-skill context.
7. **Visualiser integration** — the research document types registered and rendered in the library so briefs, outlines, findings, syntheses, and reports are browsable.

### Terminology

The word "topic" is reserved for the user-facing names only; the skill's internal vocabulary avoids it to prevent the overload it used to carry:

- **Subject** — the whole thing being researched, one per `meta/research/topics/<slug>/` set. A subject has a brief, an outline, many findings, a synthesis, and any reports.
- **Set** — the on-disk document collection for one subject, rooted at `meta/research/topics/<slug>/`: its `manifest.md`, brief, outline, findings, synthesis, and reports.
- **Round** — one `outline` + `conduct` cycle. `breadth` caps focus areas per round; `round_count` counts rounds.
- **Focus area** — a single question to research, listed in the `outline`. `breadth` caps focus areas per round.
- **Finding** — the immutable document produced by researching one focus area (one finding per focus area). `finding_count` counts findings accumulated across rounds.
- **Slug** — the cross-document-type identifier (a linkage thread) naming a subject; also the single positional every subcommand except `brief` takes. Resolution accepts three forms — a bare slug, the set directory, or any document within the set — all normalising to the set root (see the Slug resolution Technical Note).

"Topic" survives only in user-facing naming — the `research-topic` skill, the `meta/research/topics/` directory, and the `topic-research` document `type` — where it denotes the *subject* being researched. Renaming the per-item unit from "topic" to **finding** removes the two-senses-of-topic ambiguity earlier drafts contended with. The `type` discriminator inverts to `topic-research` deliberately: it reads as an adjective-noun doc-type label ("a topic-research document") paired with the `research-topic` skill, following the noun-first convention of the other visualiser doc types.

### Artifact contract

The six document shapes below are the stable contract future research skills consume. Field names are binding; exact prose sections may be refined during Slice 1 planning, but additions must be backward-compatible because findings are immutable once written.

All six carry the Accelerator base frontmatter (`type`, `id`, `title`, `date`, `author`, `producer`, `status`, `tags`, `last_updated`, `last_updated_by`, `schema_version`). All six set `type: "topic-research"` and are discriminated by `kind`, whose closed value set is `manifest` | `brief` | `outline` | `finding` | `synthesis` | `report`.

| Document | Extra frontmatter | Required sections |
|---|---|---|
| `manifest.md` | `kind: manifest`, `slug`, `round_count`, `finding_count`, `primary`; base `status` = set lifecycle | Subject, Set Contents |
| `brief.md` | `kind: brief`, `source_profiles` | Subject, Scope, Out of Scope |
| `outline.md` | `kind: outline` | Focus Areas (one `## Round N` checklist per round) |
| `findings/<nn>-<slug>.md` | `kind: finding`, `round`, `question`, `source_profile` | Question, Findings, Sources |
| `synthesis.md` | `kind: synthesis`, `rounds_covered` | Overview, Findings, Open Threads, Sources |
| `reports/<slug>.md` | `kind: report`, `question` | Question, Report, Sources |

Contract notes:

- **`kind` discriminator and `(type, kind)` resolution**: `kind` mirrors the work-item `kind` field (renamed here from the earlier `research_kind`). The corpus frontmatter schema and template resolution key on `(type, kind)` with a type-level fallback — a document resolves to its `(type, kind)` schema row, or to the type-default `(type, "")` row when none exists — so each `kind` carries its own required fields and base-`status` vocabulary while the existing kind-agnostic types are unaffected. Templates resolve `topic-research-<kind>` when present, else `topic-research`. This is a general mechanism, not topic-research-specific: it paves the way for per-work-item-kind templates (`work-item-<kind>` falling back to `work-item`). Slice 1 (0277) is its first implementer.
- **Sets are linkage targets**: `topic-research` is a typed-linkage source type, so work items, plans and ADRs may reference a set via `relates_to: ["topic-research:<slug>"]`. Slice 1 (0277) registers it (`LINKAGE_SOURCE_TYPES`/`SOURCE_TYPES`); full dangling-reference integrity co-lands with the 0278 indexer.
- **Set layout**: the four aggregate documents (`manifest.md`, `brief.md`, `outline.md`, `synthesis.md`) sit at the set root; findings live under `findings/` and reports under `reports/`. Neither subdirectory is separately indexed — the indexer keys only on `manifest.md`, and all sub-documents are siblings the Slice 6 detail page serves.
- **`primary`** names the sub-document a reader should land on: `brief.md` before a synthesis exists, `synthesis.md` after. `brief` writes it; `synthesise` flips it the first time it runs.
- **`source_profiles`** on the brief is a list (e.g. `["web", "openalex", "arxiv"]`) — the profiles `conduct` may draw on, not a single choice.
- **`outline.md`** holds focus areas grouped under `## Round N` headings, each a checklist item (`- [ ]` outstanding / `- [x]` researched) linking its finding, e.g. `- [x] What is X? → findings/01-what-is-x.md`. It is the mutable working log and the source for gap-detection (an unchecked item without a finding is what `conduct` researches next). It is exempt from the anti-changelog rule; the immutable ledger is the findings themselves, each stamped with its `round`, so `outline.md` may be freely rewritten. Finding-existence is ground truth; `conduct` reconciles the checkbox to match.
- **A finding's `question` field** holds the focus area's question — the focus axis of that researcher's spawn. The source axis is carried by `source_profile`; the two are orthogonal, so a researcher is fully specified by `(source_profile, question)`. Because `synthesise` and `report` run inline rather than spawning a researcher, neither carries a per-spawn focus field: `synthesise` aggregates all the set's findings, and a report is identified by its own `question` frontmatter.
- **Reputation tiers**: every entry under a finding's Sources carries an inline reputation tier, from the first finding written in Slice 1 onwards — the web profile emits tiers, so no finding is ever written untiered and the immutability rule never strands a non-conforming corpus. `synthesis.md`'s and each report's Sources are derived from the findings' tiers, never authored independently.
- **Base `status`** is the per-document corpus lifecycle (required by the canonical frontmatter standard, enforced by `corpus frontmatter validate`). Its per-shape values: findings are `complete` from first write (immutable, never `draft`); `synthesis.md` and each report are `complete` once written; `outline.md` is `complete` once it exists (its progress lives in its checkboxes, not its status); `brief.md` is `draft` during interactive scoping and `complete` once authored; `manifest.md` is the exception — its base `status` carries the set's five-state research lifecycle (see below) rather than a `complete`-once-written value, because the manifest is the artefact that tracks the whole research process. The set's research progress therefore lives in the manifest's base `status`, and the library card reads it directly.
- **The manifest's base `status`** is the set's own lifecycle, carried only on `manifest.md` (a derived rollup of the outline + corpus, never authored independently). It supersedes the earlier separate `research_status` field: the set lifecycle and the manifest's base `status` are one and the same field. The five states and their transitions:

  | Verb | From | Sets `status` |
  |---|---|---|
  | `brief` | (new set) | `briefed` |
  | `outline` | `briefed` | `outlined` — outline exists, nothing researched |
  | `conduct` | `outlined` / `researching` | `researching` |
  | `synthesise` | `researching` | `synthesised` — dossier exists, not finalised |
  | `finalise` | `synthesised` | `complete` |

  Reopens regress: `outline` or `conduct` on a `synthesised` or `complete` set returns it to `researching` and marks the synthesis stale. `synthesised` asserts only that a current dossier exists, not that every focus area is researched (interim synthesis is allowed) — completeness is what `finalise` asserts, and `finalise` refuses a stale synthesis so `complete` always reflects the final corpus. `ask` and `report` are read-only and status-neutral.

### Initial stories (vertical slices)

Each slice is independently shippable, demoable, and testable. Most cut through skill → agent → template → artifact → visualiser; Slices 2 and 4 are the deliberate exceptions — they need no new visualiser doc-type or library-entry work (Slice 4 registers only the `report` `kind` value into the existing umbrella type, rendered through the shared `LibraryDocView`) — and Slice 6 is visualiser-only.

Ordering constraints that actually hold: Slice 1 is foundational and gates the rest; Slice 5 must follow Slice 2, because Slice 5 wires override flags into the round loop Slice 2 establishes; Slice 3 must precede Slice 5, because Slice 3 carries the epic's only output-quality gate and the premise must be validated before the token-multiplying recursion engine lands; Slice 4 needs only Slice 1 (findings and a synthesis to read) and is otherwise independent; Slice 6 builds on the umbrella doc type and nested indexing from Slices 1–2.

All six slices are in scope. Slice 6 is the designated descope candidate if the epic runs long — it is the only slice whose deferral leaves the others fully shippable, since the shared flat `LibraryDocView` still renders each sub-document. Each slice becomes a child work item before implementation starts; the author records each child's id in this epic's frontmatter under `children` as it is created (added only once populated, per the omit-when-empty frontmatter rule), and the child points back via its own `parent`.

1. **Single-round web research, viewable in the library** *(walking skeleton)*. Run the full build loop once — `brief` → `outline` → `conduct` (single round) → `synthesise` — over web sources, producing `manifest.md`, `brief.md`, `outline.md`, `findings/*`, and `synthesis.md` under `meta/research/topics/<slug>/`, and browse the set in the visualiser. Kept whole despite its size: the epic's central design risk is whether the loop produces a dossier worth reading, and no single verb puts that question in front of a user — the engine with no library entry has nowhere to be read, and a library entry with no engine has nothing to show. The whole slice is the smallest increment that makes the loop observable end to end; the premise is then formally judged by the output-quality gate in Slice 3, which must land before Slice 5. Establishes: the `paths.research_topics` key and config default (+ `server/src/docs.rs` config_path_key); manifest/brief/outline/finding/synthesis templates (web-only) resolving through the 3-tier override (config path → user override → plugin default), plus per-skill `instructions.md`/`context.md` wiring; a dedicated `manifest.md` aggregate root written at `brief` time (the nested-manifest the indexer keys on), including its `primary` pointer; the generic `researcher` agent — granted WebFetch of arbitrary URLs — plus a web source profile that captures each source URL inline in findings together with its reputation tier, so the corpus conforms to the artifact contract from the first file written; the `research-topic` skill with `brief` + `outline` + `conduct` (single round) + `synthesise` on the `configure` dispatch pattern; an `outline` prompt carrying the effort-scaling rubric (1 focus area for a simple subject, 2–4 for comparisons, 10+ for broad subjects), which sizes the round at or beneath `breadth` as a ceiling — at the hardcoded `breadth: 8` the rubric's top band is unreachable until Slice 5 makes the ceiling tunable, and that conservative default is deliberate; `conduct` writing one immutable finding per focus area into `findings/`; `synthesise` writing `synthesis.md` inline from the findings; hardcoded defaults of `breadth: 8` and `depth: 1`; visualiser registration of one umbrella `topic-research` doc type (Rust enum + TS union + glyph + colour tokens + framed background + Discover-phase placement + visual-regression (VR) baselines) discriminated by a `kind` frontmatter field, indexed as a nested-manifest type keyed on `manifest.md`; tests green under `mise run check`. At epic-breakdown time (when `/extract-work-items` splits this epic into children), the visualiser doc-type registration + nested-manifest indexer wiring is a candidate seam to carve into a thin follow-on child immediately after the engine child — the engine writes conforming artifacts on disk without it, and the VR-baselined registration is separately demoable — provided the two children still land together so the end-to-end vertical demo is not lost.
2. **Iterative accretion + finalise**. Grow the knowledgebase across multiple rounds without clobbering, and close it off. `outline` gains next-round appending (a new `## Round N` checklist of focus areas); `conduct` gains gap-detection re-invocation (researches only outstanding focus areas, never rewrites existing findings, flips outline checkboxes as findings land); `synthesise` rewrites `synthesis.md` wholesale with anti-changelog discipline over the findings and synthesis (`outline.md` exempt — it is the working log); `outline`/`conduct`/`synthesise`/`finalise` keep `manifest.md`'s base `status`, `round_count`, `finding_count` and `primary` in sync as the set accretes, implementing the five-state lifecycle (`briefed → outlined → researching → synthesised → complete`) with reopen regression to `researching`; the `finalise` subcommand closes a subject off, refusing a stale synthesis and then setting base `status: complete` — the only path to that value, reversible by a later `outline` or `conduct`; tests. No visualiser work is required in this slice — round and focus-area structure becomes visible in Slice 6's detail page, not before. The round loop runs at `depth: 1` — automatic intra-finding recursion is Slice 5.
3. **Source rigour: academic sources**. Research drawing on academic sources, tiered by the same mechanism Slice 1 established for the web. Purely additive: reputation tagging already exists, so this slice adds source families and the rendering of their tiers, not the tagging itself. OpenAlex + arXiv source profiles (both keyless; Crossref and Semantic Scholar are deferred drop-in profiles); a `research.contact_email` config injected into the `mailto`/User-Agent polite pool (the courtesy identification these APIs use to grant a higher rate limit than the shared anonymous pool); arXiv Atom-XML parsing; rate-limit-aware fan-out; the brief's `source_profiles` list gains the academic profiles, and `conduct` assigns one profile per spawned researcher, so a single round may mix web and academic researchers; the academic profiles emit reputation tiers into the immutable findings exactly as the web profile does, and `synthesise` carries them forward (no separate citation agent — the dedicated final pass is deferred, a safe drop-in later because the immutable tagged findings preserve attribution); template rendering for reputation tiers, which surfaces in the shared `LibraryDocView` until Slice 6's set-level page supersedes it; the output-quality gate; tests.
4. **Consumption: `ask` and `report`**. Read the accreted corpus. `ask <slug> <question>` answers a question in conversation from the findings and synthesis, writing nothing; `report <slug> <question>` writes a formal `reports/<slug>.md` (`kind: report`) synthesising an answer from the corpus. Both are read-only over the findings and synthesis, and both may **propose** a new focus area to a subsequent `outline` when coverage is thin — applied only on explicit user confirmation, never a silent mutation, and the only way either verb touches the set. Registers the `report` `kind` value (part of the umbrella doc type — no new library entry) and the `reports/` layout and rendering. Depends only on Slice 1 (findings + synthesis to read). No new library-entry work — reports render through the shared view until Slice 6. Tests.
5. **Tunable depth & breadth**. Control breadth/depth via config (project + user) and per-invocation overrides. `breadth` is the hard ceiling on focus areas a round may commission (bounding `outline`); `depth` is the recursion limit within any one finding (bounding `conduct`), defaulting to 1 (no recursion), and this slice delivers that recursion engine (narrowing per level when `depth > 1`). Config-schema extension for numeric `depth` / `breadth` (a new tunable precedent), config-read plumbing, per-invocation override flags (`--breadth` on `outline`, `--depth` on `conduct`, alongside the slug positional; resolution order flag > config > hardcoded default), `configure help` docs; tests. The cost knob and the recursion engine ship together because the knob is what makes the recursion affordable to try — `depth > 1` multiplies spend, so shipping the recursion without a tunable ceiling would be the expensive ordering. At epic-breakdown time, the tunable-config surface and the `depth > 1` recursion engine are a candidate seam to carve into two children — the knob is independently shippable and the recursion engine is the acknowledged descope — ordered adjacently so the knob still lands with the recursion it makes affordable. If the epic runs long, drop the recursion-engine child and keep the knob rather than deferring both.
6. **Topic-research detail page + sub-document navigation** *(visualiser-only)*. A topic-research library entry opens a set-level detail page that represents the whole research set — the brief, the outline, its findings, the synthesis, and any reports — and navigates into each sub-document, rather than the flat shared `LibraryDocView`. Needs a way to serve a set's sibling documents (a new set endpoint, or an augmented detail response — see Open Questions) and reads `manifest.md`'s `primary` pointer to choose the default sub-document (brief before a synthesis exists, synthesis after). A Claude Design prototype of the visualiser already exists (Claude Design is Anthropic's visual design canvas, driven from Claude Code via the `design` skill) but does not yet cover topic-research, so extending it is in-slice work: prototype the set-level page there first, then implement against the umbrella doc type and nested indexing established in Slices 1–2.

## Acceptance Criteria

- [ ] *(Slice 1)* Given a subject, `/research-topic brief` interactively scopes it with the user and produces `meta/research/topics/<slug>/` containing `manifest.md` (the aggregate root the indexer keys on) and `brief.md`, each conforming to the Artifact contract above, with base `status: briefed` and `primary` pointing at `brief.md`.
- [ ] *(Slice 1)* Given a slug, `/research-topic outline <slug>` writes `outline.md` — a `## Round 1` checklist of focus areas sized at or beneath `breadth` by the effort-scaling rubric — and sets base `status: outlined`. The user may hand-edit `outline.md` before conducting.
- [ ] *(Slice 1)* Given a slug, `/research-topic conduct <slug>` runs one round over the outline's outstanding focus areas, spawns parallel `researcher` agents, writes one immutable finding per focus area into `findings/`, flips the corresponding outline checkboxes, and sets base `status: researching`, `round_count` and `finding_count`.
- [ ] *(Slice 1)* Given a slug, `/research-topic synthesise <slug>` writes `synthesis.md` from the findings, sets base `status: synthesised`, and flips `primary` to `synthesis.md`.
- [ ] *(Slice 1)* Focus areas commissioned per round never exceed `breadth`; the effort-scaling rubric may only reduce the count beneath that ceiling, never raise it. At `depth: 1` this also bounds researchers per round, since each focus area is researched by one agent.
- [ ] *(Slice 1)* Every source entry in every finding carries an inline reputation tier from the first round onwards, including web-profile sources, and those tiers are carried into `synthesis.md`.
- [ ] *(Slice 1)* The research set indexes as one library entry per `meta/research/topics/<slug>/` directory via the `manifest.md` nested manifest; individual findings and reports are not separately indexed.
- [ ] *(Slice 1)* Templates resolve through the 3-tier override (config path → user override → plugin default); users can override templates and add per-skill `instructions.md`/`context.md`.
- [ ] *(Slice 1)* The single umbrella `topic-research` doc type appears in the visualiser library under the Discover phase with a glyph and framed background and passing visual-regression baselines on both darwin and linux.
- [ ] *(Slice 2)* Re-invoking `conduct` researches only outstanding focus areas, never rewrites existing findings, and `synthesise` rewrites `synthesis.md` wholesale (idempotent accretion), keeping `manifest.md`'s counts in sync across rounds.
- [ ] *(Slice 2)* `/research-topic outline <slug>` on an already-researched set appends a new `## Round N` checklist without clobbering earlier rounds, and returns a `synthesised` or `complete` set to `researching` (marking the synthesis stale).
- [ ] *(Slice 2)* The findings and `synthesis.md` read as a single dossier with no round-by-round narration; `outline.md` is exempt and retains its round-grouped checklist.
- [ ] *(Slice 2)* `/research-topic finalise <slug>` refuses to run against a stale or absent synthesis, and otherwise sets base `status: complete` — the only path to that value; a subsequent `outline` or `conduct` returns the set to `researching`.
- [ ] *(Slice 2)* The five-state lifecycle holds: `brief`→`briefed`, `outline`→`outlined`, `conduct`→`researching`, `synthesise`→`synthesised`, `finalise`→`complete`, with reopen regression to `researching`.
- [ ] *(Slice 1, proven in Slice 3)* The generic `researcher` agent is specialised for web vs academic purely by injected profile — no per-source agent required.
- [ ] *(Slice 3)* `brief.md` declares a `source_profiles` list and `conduct` assigns one profile per spawned researcher, so a single round may mix web and academic researchers.

## Technical Notes

- **Subcommand dispatch**: mirror `skills/config/configure/SKILL.md` — inline H3 sections per subcommand in one SKILL.md, with subcommands listed in `argument-hint`. Seven subcommands means the body may grow large; consider per-mode reference docs only if size warrants.
- **Slug resolution**: every subcommand except `brief` takes a single positional — a **slug** identifying the *set*, not any one sub-document — `manifest.md` is the aggregate root, and `primary` flips from `brief.md` to `synthesis.md`, so no sub-document is a stable identifier. Resolution is a **general `accelerator corpus resolve --type <type> <slug>` subcommand** on the `corpus` binary that resolves a slug to any doc type's root — a file for flat types, the set directory for nested-manifest types like `topic-research` — reusing `paths.research_topics` and canonicalise-under-root, and accepting the tolerant forms (a bare slug, the set directory, or any document within the set). `ask` and `report` take the slug plus a question argument. This mirrors the `work resolve` precedent (paths, IDs, bare numbers) and surfaces in each subcommand's `argument-hint`. `brief` is the exception — it takes a subject and creates the set. Slice 1's engine (0277) delivers the generic resolver; type-driven `topic-research` resolution depends on the doc-type registration and lands with 0278.
- **Generic researcher + profiles**: mirror the `reviewer` agent — a single generic agent spawned with a source profile, a focus, and an output-format contract injected at spawn time. The two axes are orthogonal: the **source profile** (web, academic) is the reusable, pluggable seam — the research equivalent of review "lenses" — while the **focus** is the per-spawn content the profile operates on: the focus area's question. Only `conduct` spawns researchers, each fully specified by `(source_profile, question)`. `synthesise` and `report` spawn nothing; they run inline in the skill over the immutable findings (see the Synthesis & citations note). Profiles are injected per spawn by path-passing (ADR-0005): `conduct` hands the researcher the profile skill's path plus the output-format path, read in the agent's own context — a static `skills:` preload is unsuitable because the profile varies per spawn. Profiles live under `skills/research/profiles/`.
- **Plan/execute split**: `outline` and `conduct` are deliberately separate verbs — `outline` decides the focus areas (writing `outline.md`, which the user may edit) and `conduct` executes them. This surfaces the plan/execute separation the reference systems keep internal (Anthropic's plan-to-memory, dzhng's up-front feedback), matches Accelerator's `create-plan` → `implement-plan` idiom, and avoids the dangling-proposed-round wart that folding proposal into research would create. The effort-scaling rubric lives in `outline` (it decides how many focus areas), not `conduct`.
- **Consumption verbs**: `ask` and `report` are read-only over the findings and synthesis — `ask` answers in conversation, `report` writes `reports/<slug>.md`. Neither researches. Both may surface a coverage gap and, on user confirmation, append a focus area to `outline.md` for a later `conduct`; `synthesise` separately records what is thin as Open Threads in `synthesis.md`, which a later `outline` can draw on. The documented targeted report is deliberately kept as its own verb rather than folded into `synthesise` because reports are many and on-demand while `synthesis.md` is the set's singleton dossier.
- **Visualiser doc-type checklist** (one umbrella type, not per sub-document): a single `topic-research` `DocTypeKey` variant + `all()` + `config_path_key()` + `label()` + `wire_str()`/`from_wire_str()` and exhaustiveness tests in `server/src/docs.rs`; phase membership in `server/src/api/library.rs` (`PHASES`, under "discover"); TS `DocTypeKey` union + `DOC_TYPE_KEYS` + labels in `frontend/src/api/types.ts`; glyph icon component + `ICON_COMPONENTS` in `frontend/src/components/Glyph/`; colour tokens (light/dark) + framed-background CSS rule; VR baselines (~8 PNGs across sizes × themes — mind the linux-baseline drift). The six `kind` values are a frontmatter discriminator, not separate types, so this cost is paid once. Unlike other types, `topic-research` needs a bespoke set-level detail page (Slice 6) rather than the shared `LibraryDocView`.
- **Indexer model (resolved)**: model `topic-research` as a nested-manifest doc type, reusing the existing `nested_manifest_filename()` precedent that design inventories run on (`file_driver.rs` `list` branch + `indexer.rs` `build_entry` slug-from-parent-directory). The manifest is a dedicated `manifest.md` aggregate root — not the brief or synthesis — so the set has a stable identity from `brief` time and set-level metadata (title, status, round/finding counts, `primary` pointer) lives off the sub-documents. `list` yields one entry per `meta/research/topics/<slug>/`; the `findings/` and `reports/` subdirectories and the root sub-documents are siblings the Slice 6 detail page serves, not index entries. The lister skips dot-prefixed dirs, so the skill must write a set into a temp dir and rename it in (no half-written library entry). The genuinely new work is serving a set's siblings for the detail page (Slice 6), not the listing.
- **Config tunables precedent**: the config system has no numeric tunables today (only paths, templates, agents, work integration); Slice 5 establishes that precedent in `scripts/config-defaults.sh` and the config-read plumbing.
- **Cost**: multi-agent rounds are token-heavy (~15× a chat per Anthropic); configurable depth/breadth and the effort-scaling rubric in the `outline` prompt mitigate over-investment.
- **Depth/breadth semantics (resolved)**: `breadth` is the number of focus areas a round may commission in parallel (bounding `outline`); `depth` is the number of recursion levels permitted within any one finding (bounding `conduct`), defaulting to 1 (no recursion). At `depth: 1` `conduct` is the pure execution of the outline's focus areas and going deeper is a round-level choice made by adding focus areas to the next `outline`. At `depth > 1` a single finding drills itself recursively without a human between levels, narrowing per level (the dzhng halving), delivered in Slice 5. Keeping the default at 1 makes the expensive recursion opt-in. Overrides are named flags (`--breadth` on `outline`, `--depth` on `conduct`); resolution order is flag > config (project/user) > hardcoded default (`breadth: 8`, `depth: 1`).
- **Breadth versus the effort-scaling rubric (resolved)**: `breadth` is a hard ceiling, not a target. It caps the **focus areas commissioned per round**, and the effort-scaling rubric in `outline` operates at or beneath it — a simple subject may commission 1 focus area against a `breadth` of 8, but a broad subject never commissions 10 when `breadth` is 8. This makes `breadth` a usable cost guard rather than a suggestion; a user who wants the rubric's 10+ raises `--breadth` deliberately.
- **How the two knobs compose (resolved)**: the knobs bound different things, so they multiply rather than contradict. `breadth` bounds focus areas per round; `depth` bounds recursion levels within a single finding. At `depth: 1` each focus area is one agent, so researchers per round equal focus areas per round and `breadth` alone bounds the spend. At `depth > 1` a finding's own drilling is governed by `depth` and does not consume the round's focus-area budget — recursion happens inside a finding, not alongside it — so the worst case per round is `breadth` focus areas each expanded to at most the `depth`-bounded halving series. Both numbers should be quoted together when reasoning about cost.
- **Academic providers (resolved)**: OpenAlex + arXiv, both keyless, free HTTPS APIs — no secrets-management scope. New work is a `research.contact_email` config injected into the `mailto`/User-Agent polite pool — the courtesy identification these APIs use to grant a higher rate limit, effectively required for parallel fan-out or the shared anonymous pool returns `429`s — plus arXiv Atom-XML parsing (the one non-JSON source), and rate-limit-aware fan-out. Depends on the generic `researcher` being granted WebFetch of arbitrary URLs, not just a search tool. Crossref and Semantic Scholar are deferred drop-in profiles; Semantic Scholar's optional key is the only key in scope and is a rate-limit lift only.
- **Synthesis & citations (resolved)**: inline reputation-tier tagging in the immutable findings is the source of truth; the `synthesise` subcommand reads the tagged findings and carries citations forward as it rewrites `synthesis.md` — there is no synthesis agent and no citation agent, so the component inventory stays at skill + `outline`/`synthesise`/`report` prompts + generic `researcher`. `report` derives its Sources from the same findings. The dedicated final citation pass (Anthropic) is a deferred backstop, safe to add retroactively over the same findings because they never lose attribution.
